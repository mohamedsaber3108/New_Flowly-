# تشغيل Flowly على EC2

نسخة EC2 مستقلة عن استضافة المعاينة. واجهتها React مبنية بـVite، وخادمها Node.js يقدّم الملفات وواجهات الطلبات والمساعد. قاعدة البيانات SQLite في مجلد دائم. لا تتطلب Cloudflare أو Vercel.

## المحتويات

- `server.mjs`: خادم Node وواجهات API.
- `public/`: الواجهة الجاهزة والأصول والخطوط.
- `migrations/`: مخطط قاعدة البيانات، يطبّقه الخادم مرة واحدة عند التشغيل.
- `.env.example`: نموذج الإعدادات دون مفاتيح.
- `Dockerfile` و`compose.yaml`: خيار Docker.
- `Caddyfile`: وكيل عكسي وTLS بعد ضبط الدومين.
- `flowly.service`: نموذج systemd لخادم Node مباشر.

## تشغيل مباشر

استخدم Node.js 22.13 أو أحدث. تم اختبار التوزيعة على Node 24.19.0.

```bash
cd /opt/flowly
npm install --omit=dev
cp .env.example .env
# عدّل PUBLIC_ORIGIN وDATA_DIR والإعدادات المطلوبة في .env
node --env-file=.env server.mjs
```

الإعدادات المهمة:

- `PUBLIC_ORIGIN`: الأصل الكامل الحقيقي مثل `https://flowly.your-domain.com` دون شرطة أخيرة، ليتطابق مع Origin في النماذج.
- `HOST=127.0.0.1`: خلف Caddy على نفس الخادم.
- `PORT=3000`.
- `TRUST_PROXY=1`: خلف Caddy موثوق فقط، مع منفذ التطبيق داخلي. يسمح باستخدام عنوان الزائر لتحديد المعدل بدل احتساب كل الزوار كعنوان الوكيل. عند تعريض التطبيق مباشرة اجعله `0`.
- `DATA_DIR`: مجلد دائم يملك مستخدم الخدمة صلاحية الكتابة فيه.
- `ADMIN_TOKEN`: قيمة عشوائية قوية لا تقل عن ٣٢ حرفًا لدخول مساحة متابعة الفريق `/team`. لا توضع في رابط أو داخل كود React؛ يكتبها المسؤول عند الحاجة وتبقى في ذاكرة التبويب فقط.

لنموذج systemd: أنشئ مستخدم `flowly` ومجلد `/var/lib/flowly` المملوك له، ضع الإعدادات في `/etc/flowly.env` بصلاحيات مناسبة، وانقل الملفات إلى `/opt/flowly` ثم ثبّت `flowly.service`. عدّل مسار Node إذا كان مختلفًا. لا تشغّل نسختين من التطبيق على نفس المنفذ.

## Docker

```bash
cp .env.example .env
# عدّل PUBLIC_ORIGIN وباقي القيم. compose يضبط HOST وDATA_DIR داخل الحاوية.
docker compose up -d --build
```

يفتح Compose المنفذ على `127.0.0.1:3000` فقط ويستخدم volume دائم لقاعدة البيانات. ضع Caddy على المضيف أو اربطه بالشبكة المناسبة. لا ترفع ملف `.env` إلى Git.

## الدومين والوصول

1. وجّه DNS إلى عنوان EC2 الصحيح.
2. عدّل اسم الدومين في `Caddyfile` وفي `PUBLIC_ORIGIN`.
3. اسمح بمنفذي 80 و443 في Security Group. أبقِ منفذ التطبيق 3000 داخليًا خلف Caddy.
4. شغّل Caddy وفق إعداد الخادم الفعلي.
5. اختبر الصفحة والنموذج و`/api/health` عبر الدومين الحقيقي.

## تفعيل AI

الوضع الافتراضي مساعد إرشادي يعتمد على كتالوج الخدمات. يوضّح الموقع هذه الحالة.

### AWS Bedrock على EC2

- اضبط `AI_PROVIDER=bedrock` و`AWS_REGION` و`BEDROCK_MODEL_ID` إلى نموذج متاح لحسابك ومنطقتك.
- اربط EC2 بدور IAM يسمح باستدعاء النموذج المحدّد. لا تضع مفاتيح AWS في كود الواجهة.
- يستخدم الخادم AWS SDK v3 وConverse API عبر سلسلة بيانات الاعتماد القياسية. عند استخدام Docker، راجع وصول الحاوية لدور EC2 وفق إعداد IMDS لديك.
- يجب التحقق من إتاحة النموذج وحدود الاستخدام والتكلفة في حساب AWS. لم تُجرَ مكالمات مدفوعة في هذه المهمة.

### مزوّد متوافق مع Chat Completions

اضبط `AI_API_URL` إلى endpoint كامل، و`AI_API_KEY` و`AI_MODEL`. يقوم الخادم بالطلب؛ المفتاح لا يصل إلى المتصفح.

### Dify

اضبط `DIFY_API_URL` إلى endpoint `chat-messages` و`DIFY_API_KEY`. أضف input باسم `flowly_context` إلى تطبيق Dify وأدرجه في تعليمات النظام. راجع اختيار النموذج والمعرفة والسياسات في التطبيق نفسه.

بعد ضبط المزوّد أعد تشغيل الخدمة. إذا تعذّر الاتصال بالنموذج يعود المساعد إلى الإرشاد ويقول ذلك صراحة.

## الاستشارات والمتابعة

المواعيد الحالية **طلبات مبدئية**، وليست دعوات مؤكّدة في Google Calendar أو Microsoft Calendar. النظام يمنع طلبين لنفس الوقت المخزّن ويصدر مرجعًا وملف تقويم مبدئيًا. على الفريق تأكيد الموعد وإرسال رابط الاجتماع.

لم يُربط بريد أو CRM أو منصة اجتماعات لأن الحسابات والإعدادات لم تُقدّم. لتفعيل الإشعارات والدعوات الحقيقية، أضف مزوّد البريد والتقويم والـCRM إلى واجهة الطلبات، مع التعامل مع فشل كل ربط وإعادة المحاولة. لا تحفظ بيانات العميل فقط في localStorage.

## الوصول إلى الطلبات

على توزيع EC2، افتح `/team`، وأدخل `ADMIN_TOKEN` الذي ضبطته في إعدادات الخادم. تعرض المساحة آخر ٥٠٠ طلب مع البحث، التفاصيل، تغيير الحالة، ملاحظة داخلية وتصدير CSV. الواجهات `GET /api/admin/requests` و`PATCH /api/admin/requests/:reference` لا تكشف البيانات دون الرمز. لا تحفظه في المتصفح أو أدوات التتبع. عند تأكيد الموعد أو إرسال عرض، أرسل الرسالة ورابط الاجتماع للعميل يدويًا؛ تغيير الحالة وحده لا يرسل بريدًا.

يمكن للعميل فتح `/status` وكتابة مرجع الطلب والبريد الذي قدّم به الطلب. لا تظهر تفاصيل المشروع أو ملاحظات الفريق في النتيجة. يحدّ الخادم من تكرار البحث. عند إلغاء موعد، يصبح الوقت متاحًا مرة أخرى، وتمنع القاعدة إعادة تفعيل موعد قد حجزه عميل آخر.

في المعاينة المستضافة، قاعدة D1 منفصلة عن قاعدة EC2؛ لا تنتقل الطلبات بين البيئتين تلقائيًا. يمكن للمالك فحص البيانات من إدارة الموقع.

على المعاينة المستضافة، `/team` مخصص لهوية مالك الموقع في ChatGPT. لا تستخدم `ADMIN_TOKEN` للوصول إليه. يطبّق نشر الموقع ترحيل قاعدة البيانات الجديد؛ تطبيق EC2 يطبّق ملفات SQL الجديدة مرة واحدة عند التشغيل. احتفظ بنسخة احتياطية قبل تحديث نسخة EC2 العاملة.

## النسخ الاحتياطي والتوسّع

- استخدم SQLite online backup أو أوقف الخدمة قبل نسخ قاعدة البيانات. لا تنسخ ملف SQLite وحده عشوائيًا أثناء الكتابة مع WAL.
- خزّن نسخة احتياطية مشفّرة خارج EC2 وفق سياسة الجهة، وجرّب الاستعادة.
- لتشغيل عدة نسخ أو احتياج مؤسسي أعلى، انقل مخزن الطلبات إلى PostgreSQL/RDS بدل مشاركة ملف SQLite بين خوادم.
- حدّد مسؤولية مراجعة الطلبات والرد عليها، وراجع الاحتفاظ بالبيانات قبل الإطلاق العام.

## البناء من المصدر

من مجلد المصدر، بعد تثبيت الاعتماديات:

```bash
node node_modules/vite/bin/vite.js build --config portable/vite.config.ts
node node_modules/vite/bin/vite.js build --config portable/vite.server.config.ts
```

انسخ SQL إلى `ec2-dist/migrations` وملفات التشغيل من `portable/` إلى `ec2-dist/`. لا تنسخ بيانات الاختبار أو الأسرار أو مجلدات runtime. تعتمد المعاينة المستضافة على Vinext/D1؛ توزيع EC2 يعتمد على Vite/Node/SQLite، بينما المكوّنات والكتالوج والتحقق وAPI core مشتركة.
